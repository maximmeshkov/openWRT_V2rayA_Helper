# openWRT_V2rayA_Helper

Фоновый монитор выходов v2rayA для OpenWrt. В **LuCI → Status → Overview → v2rayA outbounds** видно, какие серверы назначены каждому выходу, отвечает ли адрес сервера и за сколько отвечает контрольный HTTPS-сайт через каждый назначенный сервер.

Модуль читает `/api/outbounds` и `/api/touch`. Серверами, правилами маршрутизации и запуском ядра продолжает управлять v2rayA. Дополнительные SOCKS-порты для мониторинга не требуются. Имена выходов, число серверов и правила пользователя в коде не заданы.

Helper рассчитан на любой роутер с v2rayA: любую версию v2rayA, ядро Xray, V2Ray или `v2raya_core` и любой протокол сервера, который знает это ядро. Мониторинг и проверки работают везде, где ответы API разбираются. Изменения в v2rayA (смена сервера, сохранение RoutingA, запуск упавшего ядра) включаются для проверенных версий или по явному разрешению. Страница **Services → v2rayA Helper → Compatibility** показывает, что включено на этом роутере и почему. Проверки никогда не перезапускают рабочее ядро v2rayA.

## Установка

Откройте успешный запуск **Build and test** во вкладке **Actions** репозитория. В разделе **Artifacts** лежат архивы `openwrt-<версия>-<платформа>` для OpenWrt 23.05.5 и 24.10.8 и платформ `mediatek-filogic` (aarch64, например BPI-R3), `ramips-mt7621` (mipsel), `ath79-generic` (mips, big-endian) и `x86-64`. Внутри находятся оба IPK и файл контрольных сумм. Для другой версии или архитектуры соберите пакеты в её SDK (см. «Сборка и тесты»).

Нужны два пакета из одной сборки для вашей версии OpenWrt. Пакет `v2raya-helper` содержит монитор на C и метод чтения через ubus; он подтягивает `curl` для GeoData. `luci-app-v2raya-helper` добавляет блок на обзорную страницу и страницы в **Services**. Скопируйте оба IPK в одну папку на роутере и из неё выполните:

```sh
opkg install ./v2raya-helper_*.ipk ./luci-app-v2raya-helper_*.ipk
```

При запуске служба читает адрес v2rayA из UCI (`v2raya.config.address`). Для `0.0.0.0:порт` она использует `127.0.0.1`, для `[::]:порт` — `[::1]`, сохраняя номер порта. При привязке к конкретному IP роутера монитор подключается с этого же адреса. Если адрес в UCI отсутствует, служба подключается к `127.0.0.1:2017`. Параметр `api` позволяет указать URL вручную. При обновлении со старой версии проверьте значение `uci -q get v2raya_helper.main.api` — сохранённое явное значение имеет приоритет.

Для v2rayA с авторизацией нужен действующий JWT. В браузере с открытой сессией v2rayA он доступен в хранилище сайта, Local Storage → `token`. Сохраните сам токен одной строкой, без префикса `Bearer`, в файл на роутере:

```sh
umask 077
vi /etc/v2raya-helper.token
chmod 600 /etc/v2raya-helper.token
uci set v2raya_helper.main.token_file='/etc/v2raya-helper.token'
uci commit v2raya_helper
/etc/init.d/v2raya-helper enable
/etc/init.d/v2raya-helper restart
ubus call v2raya-helper status
```

У v2rayA 2.2.7.4 и 2.5.10 обычный токен действует 30 дней. При отказе авторизации блок сообщает об этом. После замены файла монитор перечитает его при очередном опросе.

## Как читать показания

| Показание | Что было измерено |
| --- | --- |
| **TCP connected** | Роутер установил TCP-соединение с указанным портом. Показано время соединения после разрешения имени. |
| **Local port open** | Ответил TCP-сервис на loopback самого роутера. У туннеля за этим сервисом может быть отдельный сбой. |
| **QUIC response** | Для TUIC, Juicity, Hysteria2 или XHTTP через HTTP/3 получен ответ QUIC Version Negotiation от одного из адресов сервера (проба уходит на первые четыре адреса из DNS). Сервер с маскировкой может игнорировать эту пробу. |
| **HTTP 204 · … ms** в **HTTPS via server** | Helper получил ожидаемый ответ контрольного сайта через этот сервер. Время включает установление соединений, авторизацию в прокси, TLS и ответ сайта. |
| **HTTP 403** или другой неожиданный код | Прокси передал ответ сайта, но код отличается от ожидаемого. |
| **TLS error / Timed out / Probe error** | Контрольный HTTPS-запрос не удался. Через пробное ядро недоступный сервер выглядит именно так: SOCKS принимает соединение, а TLS обрывается. Для автосмены такая проба считается неудачной. |
| **HTTP response** в колонке **Through outbound** | У уже настроенного Xray Observatory есть свежий ответ для точного тега выхода с одним участником. Задержка включает запрос к контрольному URL. |
| **Unsupported probe / No measurement** | Тип транспорта не определён однозначно, для него нет проверки либо нет подходящих данных Observatory. |

Проверки порта и QUIC не выполняют авторизацию в туннеле. Для групп показания адресов относятся к отдельным участникам. Пустые выходы видны сразу. Перед публикацией результата монитор повторно запрашивает назначения. При обнаруженной смене профиля старая проба отбрасывается. При недоступности API сохраняется список с пометкой об устаревших данных.

Для XHTTP монитор уточняет транспорт по сгенерированной конфигурации Xray, сверяя тег выхода, адрес и порт с назначением v2rayA. При TLS и единственном значении ALPN `h3` он использует QUIC. Для `h2` и сочетания `h2,h3` Xray выбирает HTTP/2, и монитор проверяет TCP. При отсутствии совпадения в конфигурации отображается **Unsupported probe**. [Выбор версии HTTP в Xray 25.10.15](https://github.com/XTLS/Xray-core/blob/v25.10.15/transport/internet/splithttp/dialer.go#L72-L97)

При проверке непрерывности трафика оставьте назначения серверов прежними на несколько циклов опроса. В v2rayA 2.2.7.4 и 2.5.10 назначение сервера даже отдельному тестовому выходу перезапускает общий процесс Xray. Действующие соединения при этом могут оборваться. [v2rayA 2.2.7.4](https://github.com/v2rayA/v2rayA/blob/v2.2.7.4/service/core/v2ray/processManager.go#L240-L249) · [v2rayA 2.5.10](https://github.com/v2rayA/v2rayA/blob/v2.5.10/service/kernel/v2ray/processManager.go#L392-L410)

### Один HTTPS-запрос через каждый сервер

При локальной установке helper берёт назначения из API v2rayA и параметры каждого назначенного сервера из конфигурации работающего ядра. Затем открывает собственное соединение с сервером и запрашивает `https://cp.cloudflare.com/generate_204` через него. Новый выход попадает в следующую очередь проверок, даже если ни одно правило не направляет в него трафик. Для группы серверов есть отдельное показание каждого участника. У выхода без назначения отображается **No server selected**.

Простые SOCKS5-, HTTP- и HTTPS-прокси helper проверяет сам через libcurl. Все остальные протоколы (VLESS, VMess, Trojan, Shadowsocks, REALITY, XHTTP, WebSocket, gRPC и другие, которые знает ядро) идут через **пробное ядро**:

- это отдельный процесс того же бинаря, что запустила v2rayA (`xray`, `v2ray` или `v2raya_core`), либо заданного в `probe_core`;
- он получает свой конфиг через stdin: по одному входу SOCKS на `127.0.0.1` для каждого проверяемого сервера и копию выхода этого сервера из конфигурации v2rayA;
- метка сокета сервера сохраняется, иначе ставится `mark`, поэтому проба не попадает в прозрачный прокси;
- пробное ядро живёт только на время одной партии проверок и всегда завершается после неё. Рабочее ядро v2rayA, его PID и правила прозрачного прокси при этом не меняются.

TLS к серверу выполняет само ядро, с настроенным отпечатком и REALITY, как в реальном трафике. Пока партия идёт, на роутере работает ещё один процесс ядра; на слабых устройствах учитывайте эту память. Цепочки прокси (`proxySettings`, `dialerProxy`) получают **Unsupported probe** с причиной. Пока helper не нашёл ядро, проверяются только простые прокси.

Используйте один HTTPS-ресурс с известным кодом ответа. Тело ответа дальше 64 КиБ helper не читает: для проверки достаточно строки статуса. Чтобы сменить контрольный сайт, задайте `node_url` и `node_code` в настройках helper. Сертификат конечного сайта проверяется на каждой пробе. Ответ с перенаправлением показывает код первой страницы. Профильные учётные данные остаются в памяти процесса и не попадают в снимок.

## Настройки

Параметры хранятся в `/etc/config/v2raya_helper`, секция `main`.

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `api` | из `v2raya.config.address` | URL v2rayA без суффикса `/api`. Для удалённой установки требуется HTTPS с доверенным сертификатом. Пробы исходят с машины, где запущен монитор. |
| `xray_config` | `/etc/v2raya/config.json` при автоматическом выборе локального API | Файл конфигурации ядра (любого), которым управляет эта v2rayA. При ручном задании `api` чтение файла включается только явным указанием `xray_config`. |
| `allow_unverified` | пусто | Точная версия v2rayA, для которой вы разрешаете изменения без проверки, например `2.5.16`. Обновление v2rayA снова выключает разрешение. Кнопка на странице **Compatibility** ставит это значение. |
| `probe_core` | бинарь работающего ядра | Ядро для пробного процесса, если helper не может найти рабочее ядро сам. |
| `token_file` | пусто | Путь к файлу JWT. Содержимое не публикуется через ubus. |
| `login_file` | пусто | Путь к отдельному закрытому JSON-файлу с полями `username` и `password` для штатного обновления JWT. |
| `interval`, `timeout` | 10 и 3 с | Интервал повторных проб и предел времени одной пробы. |
| `workers` | 2 | Количество параллельных проверок, от 1 до 16. При большой очереди следующие выходы проверяются партиями. |
| `mark` | `0x80` | Марка исходящих проверочных сокетов для обхода штатного прозрачного прокси v2rayA на Linux. `0` отключает маркировку. Пользовательские правила PBR и выбор WAN продолжают действовать. Разрешение имён выполняет настроенный на роутере резолвер. |
| `observatory` | пусто | Полный loopback URL **уже работающего** Xray Metrics, например `http://127.0.0.1:39179/debug/vars`. Там должны быть данные именно от ядра наблюдаемой v2rayA. |
| `observatory_max_age` | 60 с | Максимальный возраст результата Observatory. Показание должно быть новее обнаруженного назначения сервера. |
| `node_url`, `node_code` | `https://cp.cloudflare.com/generate_204`, 204 | Общий контрольный адрес и ожидаемый HTTP-код. Для сквозной пробы нужен локальный файл `xray_config`. |
| `node_interval`, `node_timeout` | 60 и 8 с | Интервал повторной проверки сервера и предел времени запроса. |
| `recover_xray` | 0 | Запуск локального ядра после подтверждённого завершения его процесса. Включается отдельно через `option recover_xray '1'`. |
| `restore_lan_redirect` | 0 | Возврат одного пропавшего штатного правила входа LAN для native nftables REDIRECT. Включается отдельно через `option restore_lan_redirect '1'`. |

После изменения UCI выполните `/etc/init.d/v2raya-helper restart`. Монитор не вызывает штатные `pingLatency` и `httpLatency`. До 2.5.15 включительно первая операция временно снимает прозрачное проксирование, а HTTP-тест останавливает рабочее ядро; только 2.5.16 проверяет задержку отдельным процессом. [Исходники v2rayA 2.2.7.4](https://github.com/v2rayA/v2rayA/blob/v2.2.7.4/service/server/service/latency.go) · [Формат метрик Xray 25.10.15](https://github.com/XTLS/Xray-core/blob/v25.10.15/app/metrics/metrics.go#L61-L79)

`GET /api/version` заставляет v2rayA запустить бинарь ядра для проверки версии, поэтому helper спрашивает его один раз на процесс v2rayA, а не каждый цикл.

## Совместимость

| Что | Где работает |
| --- | --- |
| Мониторинг, проверка адреса, HTTPS через сервер, обновление токена | Любая v2rayA, чьи ответы `/api/outbounds` и `/api/touch` разбираются. Ядро helper находит как дочерний процесс v2rayA с `run --config=<этот config.json>`, имя бинаря не важно. |
| Смена сервера, сохранение RoutingA, запуск упавшего ядра, возврат правила REDIRECT | Проверенные версии: v2rayA 2.2.6.7–2.2.7.5 с Xray (OpenWrt 23.05, 24.10 и 25.12 ставят 2.2.6.7, 2.2.7.3 и 2.2.7.5). 2.2.7.4 прошла стенд восстановления. Для остальных git diff исходников v2rayA не показывает изменений в подключении серверов, управлении процессом, RoutingA и правилах REDIRECT; добавились только белые списки TPROXY в 2.2.7.4. RoutingA сохраняется на этих версиях с любым ядром. |
| Другие версии v2rayA и ядра | Только чтение, пока вы не разрешите изменения для точной версии (`allow_unverified` или кнопка на странице **Compatibility**). Разрешение не включает возврат правила REDIRECT, а смену сервера даёт только для 2.2.x с Xray: начиная с 2.3 и с ядром V2Ray подключение добавляет сервер в выход, а не заменяет его. В 2.5.16 сохранение RoutingA перезапускает работающее ядро. |
| libcurl старше 7.80 | Запуск ядра, возврат REDIRECT и обновление токена выключаются; мониторинг работает. Им нужна проверка процесса, принявшего соединение. |
| fw3 / iptables | Диагностика правил входа LAN. Возврат правила только для nftables. |

Проверка конфигурации ядра берёт команду из таблицы ядер: `xray run -test -c stdin:` для Xray и `v2raya_core`, `v2ray test -format=json -c /dev/stdin` для V2Ray v5. Вариант для V2Ray v5 ещё не запускался на настоящем бинаре.

После аварийного завершения helper служба `procd` по умолчанию повторяет запуск через пять секунд без ограничения числа попыток. Если администратор задал параметры `respawn_threshold`, `respawn_timeout` или `respawn_retry` в `system.@service[0]`, helper использует их. Штатный Stop службы прекращает попытки.

При исчезновении или замене `/var/run/v2raya-helper` работающий helper завершает работу. На следующем запуске он создаёт отсутствующий штатный каталог с правами `0700`, заново загружает доступные контрольные файлы и публикует свежий статус. Helper отклоняет симлинк, чужой каталог или неприемлемые права и ждёт штатного повтора запуска. История и контрольные файлы, исчезнувшие вместе с каталогом, накапливаются заново.

### Входящий трафик LAN

Для распознанного штатного REDIRECT v2rayA 2.2.x helper отдельно читает правила на входе из LAN через установленный `nft` или `iptables-save`. При подтверждённом отсутствии штатного перенаправления в обзоре появляется предупреждение с указанием IPv4 или IPv6. При этом результаты HTTPS через сервер остаются доступны. Helper читает правила в своём сетевом пространстве, сверив его с v2rayA и работающим Xray.

В `snapshot.lan_ingress` доступны `mode`, `backend`, `ipv4` и `ipv6`. Значения `attached` и `missing` описывают штатное правило, `unknown` означает, что для этой семьи его состояние определить не удалось. Наличие правила само по себе не подтверждает доступ из LAN. Для неподдерживаемых режимов или нераспознанных наборов правил поле может отсутствовать.

Для распознанного штатного TPROXY helper отдельно проверяет IPv4 и IPv6. В `ipv4_reason` и `ipv6_reason` возможны `hook_missing` (пропал перехват входящего трафика), `policy_missing` (пропало правило маршрутизации пакетов с меткой) и `local_route_missing` (пропал локальный маршрут в таблице 100). LuCI показывает подтверждённую причину для каждой затронутой семьи. При неоднозначном результате, например при конфликте с более ранним правилом маршрутизации, состояние будет `unknown`. Проверка TPROXY только читает конфигурацию и состояние ядра.

Если в текущем запуске helper уже видел штатный REDIRECT через `inet v2raya`, он может отдельно обнаружить исчезновение всей таблицы. При том же процессе Xray и прежнем файле конфигурации два успешных просмотра списка таблиц подтверждают `reason: "table_missing"`. В LuCI появляется отдельное предупреждение. Для IPv6 используется последнее подтверждённое наблюдение. Ошибка чтения или запуска `nft` не считается потерей таблицы.

При явном включении `restore_lan_redirect` helper может вернуть одно отсутствующее правило в прежнюю пустую цепочку `tp_pre` таблицы `inet v2raya`. Поддерживается штатный REDIRECT через nftables на локальной v2rayA проверенной версии (2.2.6.7–2.2.7.5) с Xray для IPv4 и IPv4+IPv6. Нужны числовой HTTP-адрес самого роутера и абсолютные пути к токену и конфигурации Xray. Helper сначала наблюдает рабочее правило. Затем он подтверждает его отсутствие в двух опросах с интервалом не менее секунды, проверяет настройки, состояние v2rayA, прежний сокет Xray и идентичность правил. Ядро применяет добавление только при неизменном поколении nftables. Успешный возврат правила фиксируется в журнале helper. Штатный Stop продолжает управляться v2rayA.

Эта настройка означает согласие на восстановление и при ручном удалении того же правила. Для iptables, TPROXY, нестандартных правил, пользовательских хуков v2rayA или исчезновения всей таблицы доступна только поддерживаемая диагностика.

Служба сохраняет факт наблюдения штатного правила в приватном файле `/var/run/v2raya-helper/lan-redirect`. После перезапуска helper использует сохранённые данные только в той же загрузке системы, при прежних процессах, конфигурации, сокете и наборе правил. Он заново подтверждает пропажу двумя наблюдениями и сверяется с API v2rayA перед записью. Для проверки конфигурации helper сохраняет метаданные и отпечаток. При ручном запуске путь можно передать как `--redirect-state PATH` в каталоге владельца процесса с правами `0700`. При отсутствии действительного наблюдения helper ждёт появления штатного правила.

### Восстановление процесса ядра

Ниже «Xray» означает ядро, которое запускает v2rayA: helper узнаёт его по процессу и конфигурации, а не по имени бинаря. Сам запуск после падения разрешён для проверенных версий v2rayA (см. «Совместимость») или по вашему разрешению для точной версии; иначе сводка показывает причину, а мониторинг продолжает работать.

Для восстановления нужны локальный HTTP API v2rayA с числовым адресом и явным портом (адрес со слэшем в конце тоже подходит), рабочий `token_file` и конфигурация ядра. Поддерживаются loopback и назначенные адреса самого роутера, включая IPv6 вне link-local. Helper проверяет назначение адреса перед подключением, поэтому адрес может появиться после запуска службы. Helper проверяет, что Xray принадлежит отслеживаемому процессу v2rayA и принимает TCP на своём SOCKS-порту. При выключенном SOCKS проверяется штатный локальный вход Xray `api-in`. Если helper застал Xray уже упавшим, он проверяет владельца API и убеждается, что у него нет ни одного живого дочернего процесса. Штатный запуск Xray в v2rayA 2.2.7.4 требует повторно подтвердить отсутствие процесса и получить `running=true` от API. При `running=false` запуск пропускается. Проблемы отдельного сайта или выходного сервера при живом Xray не запускают восстановление процесса.

Перед запуском helper сверяет занятые TCP- и UDP-порты со входами в сгенерированной конфигурации Xray. При конфликте на фиксированном входе он ждёт освобождения порта. В REDIRECT это относится и к сокетам на LAN-адресах, когда Xray настроен слушать на всех адресах. Это ожидание не расходует лимит запусков.

Если первый запуск ядра при загрузке v2rayA не удался, API 2.2.7.4 может вернуть `running=false`, как и при ручной остановке. Helper сохраняет это состояние. Повторный запуск Xray из v2rayA позволяет восстановить доступ после устранения причины сбоя.

Между попытками запуска проходит не менее минуты. После трёх попыток helper ждёт возвращения рабочего процесса. Если последняя проверка уверенно отменила запуск до отправки запроса, helper восстанавливает счётчик предыдущей попытки. Во время подтверждённого падения сводка показывает причину вместо успешных независимых HTTPS-проб. v2rayA не предоставляет атомарного «запусти, если всё ещё нужен запуск», поэтому совпавшая по времени ручная остановка остаётся ограничением API.

Служба OpenWrt сохраняет факт работы Xray и историю попыток в приватном файле в `/var/run/v2raya-helper`. После перезапуска helper использует эти данные только для того же экземпляра v2rayA в текущей загрузке роутера. Отсутствие Xray и статус `running` проверяются заново. Если v2rayA уже запустила своё ядро после перезапуска, helper следит за дочерним Xray текущего экземпляра. Старый Xray со своим портом может продолжать работать на время восстановления. При ручном запуске helper путь можно задать через `--recovery-state` в каталоге владельца процесса с правами `0700`.

### Обновление доступа к v2rayA

Опция `login_file` позволяет helper войти через штатный API, если файл токена отсутствует или v2rayA отклонила токен. Вход устроен одинаково в v2rayA 2.2.7.4 и 2.5.16, поэтому версия не проверяется. Нужны тот же числовой HTTP-адрес, что и для восстановления процесса, и libcurl 7.80 или новее. Пакет сохраняет `/etc/v2raya-helper.token` и `/etc/v2raya-helper-login.json` при обновлении прошивки с сохранением настроек; файлы по другим путям добавьте в `/etc/sysupgrade.conf`. Укажите абсолютные пути к двум отдельным файлам в защищённых каталогах, например `/etc/v2raya-helper-login.json` и `/etc/v2raya-helper.token`. Файл входа принадлежит пользователю helper, обычно root, и имеет права `0600`. Он содержит поля `username` и `password`.

При включённом восстановлении Xray или обновлении токена фоновый helper проверяет владельца принимающего TCP-сокета перед отправкой HTTP. Новый токен записывается атомарно с правами `0600` после проверки в авторизованном запросе. Между попытками входа проходит не менее минуты. Работающие v2rayA и Xray для такого обновления продолжают обслуживать подключения.

## Services → v2rayA Helper

**Compatibility** показывает версию v2rayA и ядро, путь и возраст процесса ядра, его геофайлы, чем проверяются серверы и какие изменения helper может делать на этом роутере, с причиной для выключенных. Для непроверенной версии здесь есть кнопка «разрешить на мой риск»; разрешение относится только к этой версии.

**RoutingA** добавляет правило с предпросмотром. Выбор выходов загружается из v2rayA. Первое совпавшее правило выигрывает. По умолчанию новое правило добавляется в конец, а кнопка **Choose rule…** открывает поиск по содержимому существующих правил и позволяет вставить перед выбранным. На v2rayA 2.2.x сохранение записывает текст в базу, и правило вступает в силу при следующей штатной пересборке конфигурации. На непроверенной версии страница предупреждает, что сохранение может перезапустить ядро. Для регулярных выражений, Geosite и GeoIP helper проверяет новое правило командой проверки конфигурации работающего ядра с теми же файлами геоданных. Этот режим проверяет конфигурацию и завершает процесс до старта прокси.

**Server switching** позволяет отдельно для каждого выхода отметить резервные серверы. В разделе **Any server from a subscription** можно выбрать целую подписку. После обновления подписки helper использует её актуальный список, включая вновь добавленные серверы. Автосмена по умолчанию выключена. Можно потребовать от 3 до 30 неудачных HTTPS-проб подряд или за последние 1–180 минут. Для смены по сбоям последняя проба тоже должна быть неудачной. Форма показывает настроенный интервал, число недавних проверок текущего сервера и сколько проверок теоретически помещается в заданное окно. Отсчёт интервала начинается после окончания пробы. Очередь и время следующего запроса увеличивают разрыв между замерами. В режиме **During scheduled hours** те же сбои или серия плохих проверок допускают смену внутри заданных часов по времени роутера; плохой считается и задержка выше порога, и неудача, поэтому их чередование тоже набирает порог. Helper оценивает правила всех включённых выходов. После успешной HTTPS-проверки резерва он ещё раз проверяет текущий сервер. Смена состоится, только если сбой или превышение порога сохраняется. Дополнительная проверка занимает до `node_timeout` секунд и не увеличивает счётчик сбоев. Резервом может быть сервер любого протокола, который выполнит пробное ядро: VLESS (включая REALITY, WebSocket, gRPC, XHTTP), VMess, Trojan, Shadowsocks без плагина и простые прокси. ShadowsocksR, Trojan-Go, TUIC, Juicity и Shadowsocks с плагином v2rayA запускает через внешние плагины, поэтому они пропускаются, и helper сразу берёт следующий резерв. Смена через API v2rayA перезапускает общее ядро и может прервать открытые соединения; это единственное действие helper, которое перезапускает ядро. После попытки действует общая пауза. Очередь хранится в работающем helper. Когда пауза закончится, поиск начинается со следующего выхода в списке. Каждый выход всё равно должен выполнить свои условия и подтвердить сбой свежей пробой. Значения по умолчанию — три неудачи подряд и пауза 15 минут.

За один цикл helper проверяет резерв только для одного выхода. Между такими проверками он обновляет состояние Xray и результаты мониторинга. Остальные выходы продолжают по очереди. Ожидание в очереди сохраняет серию последовательных сбоев. Для смены нужна свежая проверка, а режим «за N минут» учитывает только неудачи внутри заданного окна.

Перед автоматической сменой helper сверяет свежий ответ резерва и время повторной проверки текущего сервера. Если исходный замер успел устареть за время этих двух проверок, серия замеров остаётся основанием для решения. Окно «за N минут» и пауза по-прежнему проверяются перед запросом на смену.

Общая пауза измеряется по времени работы системы и сохраняется при перезапуске helper. Если роутер загрузился с записью о предыдущей попытке, прошедшее время считается от начала текущей загрузки. Helper учитывает и паузу предыдущего выхода, и паузу текущего. Расписание использует местное время роутера. Старая запись с датой в будущем переносится на новый счётчик с полной паузой от момента обнаружения.

Кнопка **Exclude** добавляет в черновик выбранного выхода исключение по адресу и порту. После сохранения оно имеет приоритет над подписками и ручным выбором. Переименование сервера, его удаление и повторное появление с тем же адресом и портом сохраняют действие исключения. Его можно снять в **Always excluded**, даже пока сервер отсутствует в каталоге.

**Latency** показывает HTTPS-замеры нескольких выходов на одном графике за 1, 6 или 24 часа. Выходы можно скрывать галочками. Цвет линии соответствует выходу, кружки отмечают проверки резерва, а тайм-ауты и ошибки вынесены в отдельную строку для каждого выхода. История накапливается в RAM с момента включения и очищается при перезагрузке роутера. График использует тот же опрос, что и мониторинг с автосменой.

**GeoData** обновляет или восстанавливает списки GeoIP и GeoSite с раскладкой файлов OpenWrt, которую использовали `update-geo-safe.sh` и `restore-geo.sh`: `geoip.dat` и `geosite.dat` в `/usr/share/v2ray`, `russia-geosite.dat`, `russia-geoip.dat` и необязательный `itdog-geosite.dat` в `/usr/share/xray`. Бинарь ядра, его вид и каталог геофайлов helper берёт у работающего ядра. Загрузка идёт программой `curl`, которую пакет ставит как зависимость. Helper проверяет загруженные файлы и текущую конфигурацию до замены. Для отката он хранит предыдущую копию и может прочитать существующие файлы `.working` из `/root/geo-backup`. Ядро подхватит файлы при следующем штатном запуске.

Compatibility, RoutingA, Server switching и GeoData используют отдельные права записи LuCI. Перед каждой записью helper заново спрашивает версию v2rayA и сверяет её с таблицей проверенных версий. Источник учётных данных для API — тот же защищённый файл, который использует монитор.

## Данные для экрана

`ubus call v2raya-helper status` возвращает время роутера `router_unix` и объект `snapshot`. Тот же снимок локально доступен в `/var/run/v2raya-helper/status.json`. Файл обновляется атомарно. Чтобы показать актуальное показание, проверьте `snapshot.state == "ok"` и `snapshot.fresh_until` по времени роутера. В `outbounds[]` есть имя выхода, `members[].server` для проверки адреса и `members[].https` для запроса через сервер. В `https` доступны `state`, `checked_at`, `target`, полученный `http_code` и при успехе `ms`. Поле `route` хранит отдельные показания Observatory, если он настроен. У показаний есть тип, время последней пробы и, при успехе, задержка `ms`. Доступ для LuCI ограничен методом `status`. Отдельный сетевой порт монитор не открывает.

## Сборка и тесты

CI собирает пакеты в официальных SDK OpenWrt 23.05.5 и 24.10.8 для четырёх платформ и прогоняет тесты на собранном бинаре под qemu-user. Тот же сценарий можно запустить локально на Ubuntu 22.04 с пакетами из `.github/workflows/build.yml`, включая `libcurl4-openssl-dev`, `libjson-c-dev` и `qemu-user`:

```sh
bash .github/sdk-package.sh 24.10.8 ath79/generic /tmp/packages
```

Скрипт проверяет архив SDK по `.github/openwrt-sdk.sha256` и подключает feeds на зафиксированных коммитах. qemu-user 6.2 возвращает в `SO_ERROR` errno хоста, поэтому на MIPS под эмуляцией отказ соединения выглядит как общая ошибка; тест это учитывает, на настоящем роутере отказ распознаётся.

Для сборки IPK вручную скопируйте этот каталог в `package/v2raya-helper` в официальном SDK нужной версии и платформы OpenWrt. В корне SDK с подключёнными штатными feeds выполните:

```sh
./scripts/feeds update -a
./scripts/feeds install libcurl libjson-c ca-bundle rpcd luci-mod-status
printf '%s\n' CONFIG_PACKAGE_v2raya-helper=m CONFIG_PACKAGE_luci-app-v2raya-helper=m >> .config
make defconfig
make package/v2raya-helper/compile V=s
```

Для локальных тестов под Linux нужны компилятор C, заголовки libcurl и json-c, а также Python 3. Тесты поднимают локальные сервисы и запускают тот же процесс, что используется на роутере.

```sh
cc -std=gnu11 -O2 -Wall -Wextra -Werror src/*.c -lcurl -ljson-c -o /tmp/v2raya-helper-test
V2RAYA_HELPER=/tmp/v2raya-helper-test python3 -m unittest discover -s tests -v
```

Тест восстановления запускает отдельные v2rayA 2.2.7.4 и Xray 25.10.15. Он завершает только дочерний процесс стенда, проверяет доступ через SOCKS и штатное обновление авторизации. Запускайте от обычного пользователя в изолированной Linux-среде с Python 3.9 или новее, curl и openssl.

```sh
python3 tests/xray_recovery_lab.py --helper /tmp/v2raya-helper-test \
  --v2raya /path/to/v2raya --xray /path/to/xray --assets /path/to/geodata
```

Добавьте `--transparent-lan` к той же команде, чтобы проверить восстановление HTTPS из отдельного клиентского сетевого пространства без настройки прокси в клиенте. Нужны `ip`, `nft`, `unshare`, `nsenter` и поддержка пользовательских и сетевых пространств Linux. Стенд создаёт свой вход Xray и правило TPROXY. Счётчик nft подтверждает перехват запроса.

Режим `--tproxy-ingress-loss --ingress-dual-family` проверяет штатный TPROXY v2rayA через `iptables` и `ip6tables`. Стенд по одному удаляет перехват, правило маршрутизации и локальный маршрут для каждой семьи. Он проверяет причину в снимке, сбой HTTPS у LAN-клиента и восстановление доступа после возврата удалённого объекта при том же процессе Xray. Сценарий также проверяет реакцию на конфликтующее правило маршрутизации.

Добавьте `--helper-restart`, чтобы завершить helper и Xray, запустить новый helper при том же процессе v2rayA и проверить восстановление клиентского HTTPS. Сценарий можно объединить с `--transparent-lan`.

Режим `--server-failover` сам поднимает отдельного LAN-клиента. Он проверяет недоступность общего контрольного сайта при двух доступных VPN-серверах и восстановление HTTPS через резерв после отказа только текущего сервера.

Режим `--late-wan` повторно запускает v2rayA с сохранёнными настройками и заблокированными в сетевом пространстве стенда соединениями к обоим VPN-серверам. Он проверяет, что неудачные пробы не меняют назначение и не перезапускают Xray, а после восстановления связи LAN-клиент снова получает HTTPS через исходный сервер.

Режим `--slow-reserve-failover` проверяет восстановление через резерв, который отвечает в пределах таймаута, но вместе с повторной проверкой текущего сервера занимает больше времени, чем срок свежести исходного замера.

Режим `--multi-outbound-failover` использует три выхода и отдельные домены для проверки каждого маршрута. Он проверяет общую паузу между сменами, сохранение назначения рабочего выхода и переключение второго выхода только после новых сбоев.

Режим `--early-xray-crash` проверяет падение Xray до запуска helper и сохранение работающего Xray при неверно указанной конфигурации. Режим `--cold-start` занимает один SOCKS-порт при запуске v2rayA и проверяет реакцию на последующую ручную остановку. Оба режима используют изолированного LAN-клиента.

Режим `--without-socks` выключает пользовательские SOCKS- и HTTP-входы на стенде и проверяет восстановление LAN через наблюдение за штатным входом Xray API. Если старый API-порт занят, helper запрашивает запуск с выбором нового номера только после подтверждения, что порт настроен как автоматический и старый номер недоступен для выбора по TCP IPv4. С `--fixed-xray-api-port` стенд проверяет ожидание освобождения фиксированного порта.

Режим `--inbound-port-case` проверяет конфликты при свободном TCP-порту SOCKS. Варианты `http-v4`, `http-v6`, `socks-udp`, `socks-udp6`, `socks-udp6-shared`, `fixed-api` и `http-lan-sharing` проверяют восстановление LAN после освобождения порта. Контрольные `http-udp-control`, `http-lan-control` и `socks-udp6-disabled` проверяют восстановление при открытом постороннем сокете.

Варианты `redirect-tcp`, `redirect-udp`, `redirect-tcp6` и `redirect-udp6` используют штатный IPv4 REDIRECT v2rayA и занимают его вход на LAN-адресе IPv4 или IPv6. `redirect-http-control` проверяет, что сокет на LAN-адресе с номером отдельного loopback HTTP-входа не мешает восстановлению. Эти тесты используют `iptables` в отдельном сетевом пространстве и отдельный `resolv.conf` в пространстве монтирования.

Режим `--ingress-loss iptables` или `--ingress-loss nftables` удаляет только штатное правило REDIRECT в изолированном стенде и проверяет снимок helper при работающем Xray и недоступном HTTPS с LAN. После возврата правила стенд проверяет доступ и прежний PID ядра.

С `--ingress-loss nftables --ingress-table-loss` стенд сначала меняет отдельную таблицу `inet fw4`, затем удаляет всю таблицу v2rayA и проверяет предупреждение, состояние Xray и доступ с LAN. Проверка работает с включённым и выключенным возвратом одиночного правила.

С `--ingress-loss nftables --ingress-stop-race` стенд задерживает штатный Stop после удаления правил и до завершения Xray. Вариант `naive` проверяет поздний возврат активной таблицы после удаления уже отсутствующей. Варианты `dormant-after` и `dormant-cleanup` проверяют отказ от активации при занятом API и успешное удаление неактивной таблицы. Вариант `dormant-failed-delete` проверяет, что при ошибке удаления поколение nftables не меняется и поздняя активация может оставить перехват после остановки Xray. Сценарии выполняются в изолированном сетевом пространстве.

С `--tproxy-ingress-loss --ingress-stop-race tproxy-route` стенд проверяет, что маршрут, добавленный после очистки сетевых правил, может остаться после Stop. Следующий штатный Start удаляет остаток, восстанавливает штатную маршрутизацию и возвращает LAN HTTPS. Проверка совместима с `--ingress-dual-family`.

С `--ingress-loss nftables --restore-ingress` helper сам возвращает пропавшее правило после подтверждения сбоя. Добавьте `--ingress-dual-family` для проверки штатного правила IPv4+IPv6. Стенд проверяет живого LAN-клиента, конфигурацию, PID Xray, сохранение пользовательского правила и штатный Stop.

Вариант `--restart-ingress-helper` удаляет это правило между остановкой и запуском helper при работающем Xray. `--without-redirect-state` и `--stale-redirect-state` проверяют, что отсутствующее наблюдение и замена файла конфигурации не дают права восстанавливать правило.

Режим `--ipv6-management` проверяет восстановление и обновление токена при API v2rayA на `::1`. `--assigned-management ipv4` и `--assigned-management ipv6` делают то же на назначенном адресе роутера. С `--assigned-management-late` адрес возвращается уже после запуска helper. Стенд создаёт отдельные сетевое, пользовательское, файловое и PID-пространства из WSL от root и использует тестовый аккаунт. Посторонний слушатель должен принимать TCP без HTTP-запросов со стороны helper.

Режим `--owner-restart-dynamic` завершает только лабораторную v2rayA. Стенд проверяет, что старый Xray остался на прежнем API-порту, а новая v2rayA запустила своё ядро на другом. После падения нового ядра helper восстанавливает его, сохраняя старый процесс и его сокет. Ручной Stop проверяется отдельно.

Отдельный тест проверяет сетевую маркировку и передачу данных по одному уже открытому соединению во время проб. Для него нужны `nft`, `ip`, `unshare` и права на создание отдельного сетевого пространства Linux:

```sh
sudo python3 tests/netns_probe.py /tmp/v2raya-helper-test
```
